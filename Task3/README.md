# Защита данных при хранении и передаче

## Что здесь

[data-protection-strategy.md](data-protection-strategy.md) — классификация данных «Медикаменте», обоснование необходимости защиты каждого класса и инструменты защиты при хранении (`AT_REST`) и передаче (`IN_TRANSIT`).

Центральный артефакт — таблица «Данные, необходимость защиты и инструменты»: тринадцать классов от идентификационных данных пациента до ключей шифрования и аналитических наборов. Колонка «В чём необходимость защиты» отвечает на вопрос, что произойдёт без меры, а не повторяет уровень чувствительности.

Разделение состояний вынесено в отдельную матрицу «Меры по состояниям данных»: по каждому классу видно, что применяется при хранении и что при передаче.

| Раздел | Содержание |
|---|---|
| Классификация | уровни чувствительности, состояния данных, профиль риска и цель обработки |
| Данные, необходимость защиты и инструменты | основная таблица: класс → ущерб без защиты → набор мер |
| Реестр категорий | теги, состояния, владелец, потребители и срок хранения по каждому классу |
| Меры по состояниям данных | матрица: класс → меры при хранении → меры при передаче |
| Защита при хранении | шифрование по уровням, раздельные ключи, разделение хранилищ, файловые 1С, резервные копии |
| Защита при передаче | внешние интеграции, внутренние вызовы, унаследованные каналы, почта, съёмные носители, сертификаты |
| Управление ключами и секретами | выдача по идентичности, разделение ролей, ротация, отзыв, копирование ключевого материала |
| Автоматизированный контроль | проверки в конвейере сборки и во время работы системы |
| Реестр программных средств | функция → класс решения → рассматриваемые варианты → критерии выбора |
| Реестр аппаратных средств | HSM, аппаратные ключи, TPM, сегментация сети, носители для копий |
| Защита при обработке | дополнительный раздел сверх обязательного объёма |
| Допущения и открытые вопросы | что не задано в исходных материалах и подлежит согласованию |

## Связь с остальными заданиями

Классы данных и словарь тегов согласованы с реестром из [Task1](../Task1/data-protection.md) и не переопределяются здесь заново. Блоки защиты — `Access Control`, `Consent Registry`, `Key Management`, `Data Catalog`, `Egress Control`, `Audit Trail` — те же, что на целевой схеме в [Task2](../Task2/README.md). Ограничения существующего ландшафта взяты из анализа As-Is в [Task1](../Task1/problems.md). Возможности шифрования проверяются по отдельным участкам; TCP/IP и OLE сами по себе не доказывают отсутствие защиты.

## Что осознанно не сделано

Числовые значения стойкости, периодичности ротации, сроков хранения, доступности и восстановления в исходных материалах не заданы. Они помечены `TBD` и вынесены в раздел допущений, а не заменены правдоподобными числами: выдуманный срок хранения выглядит как требование и приводит к неверным решениям при внедрении.

Конкретные продукты указаны как рассматриваемые варианты с критериями выбора. Выбор делается после инвентаризации существующих систем и проверки совместимости.
